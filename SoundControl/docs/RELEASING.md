# Выпуск Sound Control в MicroUtils

Версия проекта — `version.py`. Тег отдельной утилиты:
**`sound-control-v1.0.0`**. Ветка разработки может называться `SoundControl`;
это не номер релиза. Другие утилиты используют собственные префиксы тегов.

## Подготовка локально

1. Обновите `version.py`, `CHANGELOG.md`, описание `docs/releases/<версия>.md` и скриншоты при изменении интерфейса.
2. Выполните тесты и сборку по [BUILDING.md](BUILDING.md).
3. Запустите `package_release.py --download` и проверьте `release/release-assets.json`, контрольные суммы и EXE.
4. Проверьте пользовательские сценарии: новая настройка, hotkey, восстановление USB/выходов, сон, обновление поверх существующего профиля.
5. Новую установку драйвера Banana проверяйте на отдельной тестовой Windows с перезагрузкой.

Файлы `release`, `vendor`, `dist*`, журналы, `.venv` и `.idea` не коммитятся.
Из исходников в релиз автоматически включаются только явно разрешённые файлы.
GitHub добавит свои `Source code (zip/tar.gz)` для всего монорепозитория;
архив `SoundControl-<версия>-source.zip` содержит только эту утилиту.

## После проверки изменений владельцем

Эта подготовка не публикует код. Следующие шаги выполняются отдельно, когда
владелец решит отправить изменения на GitHub.

1. Проверьте рабочие файлы и `.gitignore`, затем создайте commit и отправьте ветку `SoundControl`.
2. Предпочтительный путь — PR из `SoundControl` в `main`, дождаться CI и включить изменения в `main`.
3. В Actions откройте **Sound Control — release draft**, выберите нужную ветку и запустите вручную с ожидаемой версией `1.0.0`.
4. Workflow повторно выполнит тесты, соберёт файлы и создаст **черновик**, привязанный к выбранному commit/tag.
5. Откройте черновик в Releases, проверьте файлы, описание и изображения. Для стабильной `1.0.0` пункт pre-release выключен.
6. Нажмите **Publish release**, когда всё проверено. Никакой workflow не публикует релиз автоматически.

Если релиз выпускается из ветки `SoundControl` до merge в `main`, ссылки картинок
в описании указывают на конкретный commit, а не на неподготовленную ветку `main`.
Корневой каталог проектов на GitHub обновится только в той ветке, куда попадёт commit.

## Вручную через интерфейс GitHub

После отправки исходников: **Releases → Draft a new release**. Создайте тег
`sound-control-v1.0.0`, укажите commit/ветку Sound Control, заголовок
`Sound Control 1.0.0` и текст из `docs/releases/1.0.0.md`.
Замените `{{ASSET_BASE}}` и `{{IMAGE_BASE}}` точными адресами этого релиза/commit
(workflow делает это сам). Прикрепите файлы из `release-assets.json`.
Сначала сохраните черновик, затем после проверки публикуйте.

## Через GitHub CLI

После создания и отправки тега используйте команду `gh release create` с
`--verify-tag --draft --title ... --notes-file ...`. Прикладывайте только
файлы из `release-assets.json`; список уже подготовлен сборщиком.
Не используйте автоматическое создание тега из непроверенной рабочей папки.

## Контрольные суммы и происхождение

`SHA256SUMS.txt` содержит SHA-256 файлов поставки. Сверить EXE в PowerShell:

```powershell
Get-FileHash .\SoundControl-1.0.0-windows-x64.exe -Algorithm SHA256
```

`build-info.json` содержит версию, commit и зависимости. Локальная подготовка
с непроиндексированными файлами помечается `uncommitted working tree`;
публичный черновик собирается workflow из конкретного commit.
